# Note 17 — Reviewed contracts, generated bodies: typed black boxes in Monty micro-sandboxes

**Status:** prototype shipped (`examples/relay-boxes/`: framework
`boxkit/` + Relay rebuilt on it). Developer directive (2026-10-03):
*"Try another approach. Micro sandboxes with Monty. Let the developer
review the data model and state transitions. Also, the user reviews the
types of black boxes. Then let the LLM implement all functionality in
typed blackboxes. Receiving and outputting data. Side effects are
supported by passing functions and objects to the blackbox or by the
outer human-reviewed code. Each blackbox contains a human reviewed,
llm-generated description. For example, the UI code (view and HTML
template) is llm-generated. Write a DSL that splits the reviewed and
generated code to separate files."* Follow-ups from the developer: the
DSL may be plain Python decorators/conventions; guards are reviewed
code; boxes are held by types + descriptions + tests, with reviewed
tests split from generated tests.

## The idea, against what came before

Notes 13–16 made **the rule base the program**: an engine (reviewed once)
executes rules (reviewed per app, Z3-analyzed), and since note 15 a free,
agent-written UI sits above a kernel API. The unreviewed code there is
the UI, trusted for nothing.

This note keeps the kernel idea but changes *what* is reviewed. The
program is ordinary Python, split by **who reviews it**:

| reviewed by a human (`src/relay/`, `test/relay/`) | generated by an LLM (`src/generated/`, `test/generated/`) |
|--------------------------------------------|---------------------------------------------------|
| data model (`*/model.py`, `people.py`)     | every black-box body, run ONLY in a Monty sandbox — `generated.relay.X` mirrors `relay.X` |
| state transitions (plain tables in `*/model.py`), guard rules (`*/rules.py`, `policy.py`) and the kernel (`kernel.py`) | generated tests |
| box types, capabilities, signatures + descriptions (contract modules: `cases/queues.py`, `cases/pages.py`, `mail/intake.py`, `web/routes.py`, `web/ui.py`) | |
| outer code: HTTP, effects (`web/server.py`, `mail/gateway.py`) |                                  |
| reviewed tests                             |                                                   |

Code is organised by business area (`cases/`, `thread/`, `mail/`, `web/`),
not by kind of code; the generated tree mirrors the reviewed one module
for module. (The first build grouped by kind — model/machine/boxes/shell —
and hash-locked the reviewed files; both were revised, see "Revision".)

The unreviewed portion grows from "the UI" to "all functionality that is
not data model, transitions, policy or effects" — routing, every view and
template, queue logic, inbound-mail interpretation — and the question
becomes whether **types + a reviewed description + tests + a sandbox**
hold a body well enough that nobody needs to read it.

## The DSL (plain Python + one file convention)

* `@blackbox` on a typed, body-less function in a contract module; its
  docstring is the reviewed description. Lint: contract modules hold
  types and body-less boxes only.
* `Protocol` parameters = **object capabilities** (the sandbox can call
  exactly the protocol's methods on the host object — `DeskReader`, the
  kernel as one actor sees it, read-only); `Callable[...]` parameters =
  **function capabilities** (`esc`, `org_of`, another box). Everything
  else is data.
* `Policy.deny/allow(rule_id, description, on=…)` in each business
  area's `rules.py`. State transitions are NOT part of the DSL (a later
  simplification): a plain `dict[(state, action)] -> state` in the area's
  model, read by plain reviewed kernel code; their well-formedness
  (every state reachable, only tombstones final) is a reviewed test. Refusals are `Denied(rule, reason)` values. `on=` is
  mandatory: the rule engine's "untagged = root only" default failed open
  (note 16, finding 2); here that sharp edge cannot be written.
* Convention: `src/generated/` and `test/generated/` are generated and
  marked `linguist-generated` (collapsed in PR diffs); everything else is
  reviewed — in the pull request, where the reviewer sees which reviewed
  files changed. No lock file.

What boxkit derives per box, mechanically: the **stub** (the transitive
closure of reviewed types the signature names, copied verbatim, plus a
contract protocol) — the implementer's whole world, and what ty checks
the body against *inside Monty*; the **spec hash** over the text of
those types + the signature + the description (not over where they
live), recorded per box in the generated module, so a contract change
makes exactly the affected bodies STALE and a pure move makes none; the
**constructors** —
only reviewed dataclasses in the closure can be instantiated by the
sandbox; **conformance checks** on every value crossing in either
direction (dataclasses do not validate their own fields).

## What was built

* `boxkit/` (1,128 lines incl. its tests): contract extraction, Monty
  runner (pydantic-monty 1.0.0, ~2 ms per call), capability wrappers,
  runtime conformance, Policy, CLI `brief | check`. Ten framework tests, each a hostile or broken body:
  file/env/socket access, constructing an out-of-contract type, mutating
  host data, calling a non-protocol method or a private attribute,
  ill-typed capability calls, wrong result types, runaway CPU/memory,
  signature drift — all caught.
* Relay (tickets HD-1…HD-9, same as `examples/helpdesk/`): reviewed
  1,331 lines (model 115, machine 544 of which ~250 are the 29 rules,
  boxes 351, shell 321) + reviewed tests 566; generated 910 lines over 8
  boxes (route, sort_into_queues, intake_email, document, sidebar,
  queue_page, case_page, new_case_page). A real htmx UI; refusals
  render by rule name; persona switcher; inbound-mail webhook (new: the
  rule-engine Relay had the robot's *permissions* but no email parsing).
* The gate (`check.sh`, both directions): framework tests → `boxkit
  check` (contract lint, boundary lint, fresh+typed bodies) → reviewed then generated tests → five
  preserved bad variants that must FAIL at a named stage → rule-deletion
  mutation run (every guard rule's deletion must break a reviewed test)
  → boot. Full run: 72 s; 10 framework + 44 reviewed + 300 generated
  tests (the latter written by a brief-only agent; they independently
  fail the unescaped variant too), 5/5 variants caught, 29/29 mutants.

## Findings

1. **Descriptions carried the spec, except exactly where the
   implementers said they would not.** Bodies were written by sub-agents
   (a cheaper model) forbidden to read anything but their brief. Of 8
   boxes, 6 passed every reviewed test in round 1 (the 5-box UI family
   included); 2 failed — and each failure sat on a sentence the
   implementer had *itself* reported as ambiguous (reply trimming in
   `intake_email`; non-numeric path ids in `route`). The ambiguity report
   is a by-product worth keeping: it is a review checklist for the
   description, written by the only reader that takes it literally.
   Prediction for the next domain: requiring an ambiguity report per box
   and routing it to the description reviewer will catch most
   description defects *before* a test does.
2. **Per-box spec hashing is the right staleness grain.** Tightening the
   two descriptions moved exactly two hashes; the gate marked exactly
   those two bodies STALE, the other six stayed fresh (their stubs never
   contained the edited text). Round 2 (STALE line + counterexample →
   implementer) converged in one iteration each.
3. **The reviewed tests had a one-directional hole; mutation found it.**
   The reviewed policy grid (285,120 situations; the 29 safety
   properties S1–S29 and 16 witnesses P1–P16 of the rule-engine Relay)
   killed only 24/29 rule-deletion mutants: five allow rules (customer
   read, customer edit, staff attach, lead removes, robot attaches)
   could be deleted with every test green — no witness exercised them.
   This is guardrail 2 again ("the safest system does nothing"), found
   this time by mutation rather than by an agent exploiting it. Five
   witnesses (P17–P21) → 29/29; the mutation run is now a gate stage.
   (Whether the rule-engine Relay's features.yaml runs cover the same
   five rules was not checked.) The lesson: **a reviewed test suite is a
   gate only if mutation says so.**
4. **Some properties live between boxes, not in any contract.** Five UI
   boxes share a CSS class vocabulary; `case_page`'s links must be routes
   `route` knows. Neither is expressible as a box type. Resolutions used:
   generate coupled boxes *as a family* (one implementer for all five UI
   boxes — coherent in one round), and pin the cross-box property in a
   reviewed test (`test_every_rendered_link_and_form_is_a_route_the_router_knows`).
   A third option, not tried: lift the shared vocabulary into the
   reviewed contract (a class-name `Literal`).
5. **Capabilities make security properties testable instead of
   hoped-for.** Monty lacks `html`, so escaping arrives as the reviewed
   `esc` capability; whether a page *uses* it is then a reviewed test
   with hostile text on every page × persona (and the preserved
   unescaped variant must fail it). The redacted-comment body is withheld
   *by the kernel* (`body=""`), closing note 16's ME-3 hole (a rude UI
   could render redacted text) by construction: the box never receives it.
6. **Review burden moved, it did not vanish.** Reviewed non-test code is
   ~1,330 lines (1,457 after the business-area restructure) vs ~280 lines of rules (+440 of gate YAML) in the
   rule-engine Relay, whose engine is reviewed once for all apps. Here the
   kernel (~290 lines) is per-app and reviewed; the 29 rules are
   predicates over Python objects, readable but **not symbolically
   analyzed** — the policy grid is exhaustive over chosen representative
   values, not over the domain (Z3 over rules.yaml is). What was bought:
   the UI, routing and product logic (910 lines) need no review at all,
   and the developer's review is grounded in typed signatures + prose
   rather than in an engine's vocabulary.

## Revision (same day): no lock, business-area modules, a src/test mirror

The developer simplified three things after the first build:

* **The review lock went.** "The user can see in the pull request which of
  the reviewed files changed." The lock was tamper-evident, not
  tamper-proof (an agent could re-stamp it), so real enforcement lived in
  CODEOWNERS/branch protection anyway; the PR diff is the review surface.
  What makes that usable is the folder split: the generated folders are
  `linguist-generated`, so GitHub collapses them and the expanded diff is
  exactly the reviewed code.
* **Modules by business logic, not by kind of code.** `cases/`, `thread/`,
  `mail/`, `web/` each hold their model, transitions, rules, contracts and
  effects; `generated.relay.cases.pages` mirrors `relay.cases.pages`.
  A generated module holds every body its contract module declares — the
  three case pages had written byte-identical helpers independently;
  grouping gives them one home.
* **A uv src layout** with `src/generated/` beside `src/relay/` and
  `test/generated/` beside `test/relay/`; `uv_build` ships `relay`,
  `generated` and `boxkit` in one wheel.

The move was checked, not trusted: the spec hash was redefined to be
location-independent, and the hashes computed on the pre-move code equal
the post-move ones for all 8 boxes — the restructure changed no contract,
so no body needed regenerating.

Later the same day, a fourth simplification: **state transitions left the
DSL.** `Lifecycle`/`T` (with a gate stage checking reachability and
terminals) became a plain transition table per area in its `model.py` —
`CASE_TRANSITIONS: dict[tuple[CaseState, CaseAction], CaseState]` — read
by plain kernel code; reachability and "only tombstones are final" moved
into an ordinary reviewed test (verified to fail when a transition is
removed). boxkit now provides exactly two things: `@blackbox` and
`Policy`. No body went STALE: transitions were never part of any box's
contract.

## Falsifiers / next probes

* **BX-1 — description drift without hash drift.** A description can be
  satisfied by bodies that differ in ways no reviewed test pins (bounce
  wording, CSS). Measure: regenerate each box N times from the same brief
  and diff behaviour on random inputs; behaviour the descriptions leave
  free will vary — is any of it product-relevant?
* **BX-2 — the grid is not a proof.** Encode `Situation` predicates to
  Z3 (they are boolean combinations over finite enums + one date
  comparison) and check the grid's verdicts symbolically — or show a
  rule that the grid's value choice cannot distinguish.
* **BX-3 — boxes that need writes.** Every box here returns values; the
  shell applies them. A multi-step workflow (e.g. merge two cases) may
  want a box to sequence kernel writes. Test a write-capability
  (`DeskWriter` bound to the actor) and whether the kernel-as-guard
  argument still holds when generated code drives the sequence.
* **BX-4 — reviewed shell creep.** The gateway (`mail/gateway.py`) holds one
  policy-shaped check outside `POLICY` (a mail reply must come from the
  case's org). If more such checks accrete in the shell, the policy is
  not where the reviewer looks for it. Lint: shell may not compare actor
  attributes.
* **BX-5 — cost of the sandbox at product scale.** ~2 ms per box call
  and one Monty worker per nested call (a page calling `sort` holds two
  workers). Measure p99 under concurrent load and pool exhaustion.

## Verdict

The split works as a development method: a developer reviews ~1.3k lines
of typed contracts, transitions, rules and effects plus the tests; the
LLM writes everything else into micro-sandboxes it cannot escape; and the
gate — not a reader — holds the generated code to the contracts, in both
directions. The weakest link is not the sandbox (it held every hostile
body thrown at it) but the **completeness of the reviewed tests and
descriptions**: two descriptions were ambiguous, one test suite was
one-directional. Both were caught mechanically — by implementer
ambiguity reports + reviewed tests, and by mutation — which is the method
working. Compared with rules-as-the-program, this trades symbolic
analysis of the policy for a broader unreviewed surface and plain-Python
review; the two compose (the kernel in `kernel.py` could be the rule
engine's kernel), which is the obvious next experiment.
